Three thousand ETL pipelines run on an in-house orchestration platform, and the platform needs to move to a new version. Every one of those pipelines feeds something: a report, a downstream job, a reconciliation, a decision someone makes on Monday morning. None of their owners asked for the upgrade.

The technology change was hard. Keeping the people behind 3,000 workloads confident while those workloads changed underneath them was harder.

## A pipeline count is a dependency count

3,000 pipelines reads like an inventory number. Each pipeline carries upstream sources, downstream consumers, a schedule someone depends on, and an expectation about when data lands and what happens when it doesn't.

Many of those expectations are undocumented. They live with the teams who consume the data, and they surface when a load runs late or a number changes.

At that scale, a platform upgrade stops being a deployment exercise. It becomes a change programme across every team that touches the data.

## Why the upgrade itself was hard

An in-house platform has no vendor migration guide. The differences between versions are whatever the platform changed, and pipelines built on the old version encode assumptions about behaviour that nobody wrote down.

The risk categories will be familiar to anyone who has moved orchestration workloads:

| Category | What can change between versions |
|---|---|
| Compatibility | Pipeline definitions or configuration that the new version parses or validates differently |
| Scheduling and dependencies | How triggers, ordering, and cross-pipeline dependencies resolve |
| Runtime behaviour | Execution environment, resource limits, performance characteristics |
| Failure handling | Retries, timeouts, partial failures, and the state left behind |
| Data correctness | Whether the same inputs still produce the same outputs |
| Observability | Whether existing alerts, logs, and runbooks still point at the right signals |

Treat the table as the questions every pipeline has to answer. Some pipelines trip none of them. Some trip several at once, and they are rarely the ones you expect.

## Why a big-bang cutover was off the table

A single cutover puts every unknown into production on the same night. When something fails, there is no way to separate a platform defect from a pipeline-specific quirk, and no earlier evidence to reason from.

It also asks every stakeholder to accept the full risk on day one, with nothing to base that acceptance on.

The alternative is progressive migration: move a group, validate it, learn from it, fix the process, then move the next group.

```text
lower-risk workloads
  -> validate -> learn -> improve the migration process
  -> next group, slightly higher risk
  -> validate -> learn -> improve the migration process
  -> ...
  -> most critical workloads
```

Each loop produces two things. Evidence that the new platform behaves correctly, and a migration process slightly better than the one before.

## Sequencing is a risk control

The order in which workloads move is itself a risk-control mechanism. Getting it right matters as much as any technical fix.

These factors decide where a pipeline sits in the sequence:

- **Criticality**: what breaks for the business if this pipeline is late or wrong.
- **Dependencies**: how many pipelines and consumers sit downstream of it.
- **Complexity**: how much of the platform's behaviour the pipeline relies on.
- **Testability**: whether correctness can be checked with confidence before production.
- **Operational maturity**: whether the owning team can support and diagnose it.
- **Known migration risk**: whether it uses features known to differ between versions.

Early waves favour pipelines that are low on criticality and high on testability. They are cheap to get wrong and easy to prove right, which makes them the best place to find out what the migration process can't handle yet.

Dependencies constrain the order further. Moving a pipeline means knowing what feeds it and what it feeds, so waves form around dependency boundaries as much as around risk.

## Each environment answers a different question

Promoting a workload through environments is often treated as a formality. In a migration like this, each environment exists to answer a specific question, and a workload doesn't advance until that question has an answer.

```text
development      integration / test       pre-production           production
-----------      ------------------       --------------           ----------
Does it run?     Is the output correct?   Does it behave under     Can it be operated
                 Do dependencies still    realistic conditions?    and supported?
                 resolve?                 Are monitoring and
                                          performance acceptable?
```

Environment names vary between organisations. The progression holds: answer the cheap questions first, where failure costs little, and the expensive questions last, with the most evidence behind them.

A pipeline that runs cleanly in development has proven that it parses and executes. Correctness, dependency behaviour, performance, and supportability each need their own evidence, and each environment is where one layer of that evidence gets gathered.

This framing changes what a failure means. A defect found in a lower environment is the process working. The same defect found in production is the process failing.

## Testing builds confidence as well as evidence

Testing served two purposes. The obvious one was technical validation. The less obvious one was giving stakeholders something concrete to base a decision on.

A test result that stays inside the migration team builds no confidence anywhere else. The loop that matters looks like this:

```text
test -> observe -> find defects -> improve the migration approach
     -> record the evidence -> share it
     -> earn agreement for the next, riskier group
```

Evidence from early waves carries much of the weight for later ones. When an owner asks "how do we know this will work for our pipelines?", the answer can point to comparable workloads that have already moved, what went wrong with them, and what changed as a result.

## Different stakeholders carry different risks

"Stakeholders" is too coarse a word to plan with. Each group is exposed to a different failure and needs a different kind of evidence. The right-hand column below describes the kind of evidence, not a fixed checklist.

| Stakeholder | The question they are asking | Evidence that answers it |
|---|---|---|
| Engineering | Will the platform and the pipelines work? | Execution results, defect trends, compatibility findings |
| Data and application owners | Will the data stay correct? | Output validation against pre-migration behaviour |
| Operations | Can we support this after cutover? | Working monitoring, current runbooks, a clean handover |
| Business stakeholders | Will our critical processes keep running? | A track record on comparable workloads, a recovery plan |
| Leadership | Is risk going down, and are we on track? | Waves completed, defects closed, what remains and why |

Translating progress into each group's terms is part of managing the risk. A defect count means something to engineers. A data owner needs to know which of their pipelines are affected and what that means for the data they rely on.

## Closing the confidence gap

A predictable tension shows up in a programme like this. The migration team, close to the evidence, decides something is ready. The people who own the risk haven't seen enough to agree.

Both positions are reasonable. A successful test doesn't mean everyone is comfortable moving their most critical workload, and pushing past that discomfort with authority costs more trust than it saves time.

The gap closes with evidence: repeated successful waves, open reporting of what went wrong, clear ownership of each residual risk, and agreement on what has to be true before the next step. When progression criteria are agreed in advance, a go/no-go decision becomes a check against those criteria instead of a negotiation.

## The most critical workloads went last

Leaving the most critical pipelines until late can look like avoidance. Those workloads deserve the most mature version of the migration process, and that version doesn't exist at the start.

Earlier waves are where compatibility issues surface, testing gaps show up, failure modes on the new platform become familiar, and validation patterns earn stakeholder trust. The process used for the critical workloads had been shaped by every wave that came before it.

The critical workloads still carried the most risk. What had changed was how much was known about that risk, and how much evidence the people accepting it had in front of them.

## Leading the migration, not only running it

Migrating pipelines is execution. Working out how 3,000 pipelines can move safely, in what order, on what evidence, and with whose agreement, is a different job.

Most of that job comes with no formal authority. The pipelines belonged to other teams and the risk sat with their owners. What moved the programme forward was structure: a sequencing model people could challenge, progression criteria people had agreed to, and evidence that made each decision easier than the last.

Day to day, that meant understanding what had changed between platform versions, identifying where those changes put pipelines at risk, coordinating testing across teams and environments, managing issues and exceptions through to resolution, and feeding each lesson back into the process for the next wave.

## Where to start if you're facing one

1. **Map the dependency graph before the pipeline list.** The order you can migrate in is set by what feeds what, and you can't sequence by risk until you know it.
2. **Write down what each environment must prove.** If an environment has no question attached, a workload passing through it tells you nothing.
3. **Choose the first wave for learning.** Pick pipelines that are low-criticality and easy to validate, and expect them to expose gaps in your process.
4. **Map each stakeholder group to the risk it carries.** Then decide what evidence answers that risk, and report in those terms.
5. **Agree progression criteria before the first go/no-go.** Criteria agreed under pressure turn into negotiations.
6. **Hold the critical workloads back until the process has a track record.** A platform upgrade is done when the organisation can move its most important workloads with confidence, which is later than the day the new version is deployed.
